# tsukan-fm-bridge — たたき台v0

通関業務「受領書類 → AI抽出 → FileMaker下書き入力」の一番最初のたたき台。
目的は「実書類でどこまで抽出できるか」を数字（人手完成形との一致率）で示し、
FileMakerへ渡す出口の形（1案件1行のCSV）を見せること。

**このv0は精度を追い込むためのものではなく、ギャップを数字で洗い出すためのもの。**
見つからなかった／一致しなかった結果もすべて正直に出す。

---

## 前提

- 実書類（PDF/xlsxの現物）はこのプロジェクトフォルダにコピーしない。
  `config.local.json` で元パスを参照するだけ（後述）。
- 抽出エンジンはv0時点では規則ベース（正規表現）のみ。Anthropic APIは呼ばない
  （呼ぶコード・APIキーを扱うコードは本プロジェクトに一切含まれない）。
- 動作確認済み環境: Python 3.14.4（`python`/`py` とも同一実体）。
  pdfplumber 0.11.9 / pypdf 6.14.2 / openpyxl 3.1.5 / PyYAML 6.0.3 が
  最初から利用可能だった（`itrans-descente/setup/wheels/` のwhl流用は不要だった）。
  ローカルOCR（Tesseract等）は未導入・未確認 → 要OCR書類は抽出せずスキップする。

---

## セットアップ

1. `config.local.example.json` を `config.local.json` にコピーする
   （`config.local.json` は `.gitignore` 対象＝追跡されない）。
2. `config.local.json` の `cases_root`（案件フォルダの親ディレクトリの絶対パス）と
   `case_map`（`"case01": "実フォルダ名"` の対応）を実環境に合わせて書き換える。
   環境変数 `TSUKAN_CASES_ROOT` でも `cases_root` だけは上書きできる。
3. 依存ライブラリ: `pdfplumber` `pypdf` `openpyxl` `PyYAML`
   （このマシンでは追加インストール不要だった。無い環境では
   `pip install pdfplumber pypdf openpyxl PyYAML` を試し、pipが使えない場合は
   `itrans-descente/setup/wheels/` のwhlを流用する）。

## 使い方（コマンド2つ）

```
python extract.py
python compare.py
```

- `extract.py` … 案件フォルダを走査し、規則ベースで `fields.yaml` の各フィールド候補を抽出する。
  `--limit N`（先頭N案件のみ）・`--cases case01,case03`（案件指定）で部分実行もできる。
- `compare.py` … `extract.py` の結果と、各案件の人手完成形xlsx（評価管理表）を突合する。
  `extract.py` を先に実行しておく必要がある。

出力は すべて `out/`（`.gitignore` 対象・追跡されない）に書かれる:

| ファイル | 内容 |
|---|---|
| `out/<case_id>/candidates.csv` | 案件ごとの全フィールドの抽出結果（見つかった/未検出/対象外） |
| `out/fm_import.csv` | 全案件まとめ、FM取込用（UTF-8 BOM・1案件1行・fields.yaml列順） |
| `out/file_inventory.csv` | 全案件まとめ、書類ごとの分類・要OCR・文字数の一覧（検証用） |
| `out/mapping_report.md` | フィールド⇔評価管理表ヘッダーの自動対応付け結果 |
| `out/accuracy_report.md` | フィールド別・案件別の一致率（一致/不一致/未抽出/対応列なしの件数のみ） |

## 仮決め事項（要すり合わせ）

- **fields.yaml は仮スキーマ。** `IDA入力項目マスター_共通部_v0_3.md` セクションA
  【抽出】欄をそのまま転記しただけで、FileMaker側の実レイアウトは未確定。
  レイアウトが決まり次第、列対応をまるごと差し替える前提。
- **突合キーが未確定。** `評価管理表` は1案件に対して複数シート・多数行を持つ
  （実測で1案件あたり検出ヘッダー列数60〜290）のに対し、`fm_import.csv` は
  1案件1行の集計値。v0では「AI候補値が、対応付けた列のどこかの値と一致するか」
  だけを見ており、**どの行と対応するか**までは踏み込んでいない。
- **書類種の分類はヒューリスティック。** ファイル名の強い手がかり（「出荷書類」
  「INS 」で始まる等）→ 内容キーワードのスコアリング（2件以上ヒットで確信）→
  弱いファイル名手がかり、の順で決めている。誤分類はあり得る。
- **フィールド⇔ヘッダーの対応付けも単純な文字列類似度ベース。**
  `fields.yaml` の日本語ラベルとしか比較しておらず、英語表記・同義語の
  エイリアスは未整備。類似度0.5未満は「対応列なし」扱い（閾値は仮）。

## 既知の限界

- **要OCR書類はv0では一切抽出しない。** ローカルにOCR環境（Tesseract等）が
  無いため、テキスト層のない書類は「要OCR」フラグを立てて丸ごとスキップする。
  今回の10案件では、解析対象68書類中31書類（約46%）が要OCR判定になった
  （pdfplumberとPyMuPDFの2ライブラリで文字数を突合し、どちらも0〜数文字/頁
  だったことを確認済み＝ライブラリ側の抽出バグではなく実際にテキスト層が
  無いスキャンだと判断した）。特に「出荷書類」相当の束と「検査/保険」書類は
  ほぼ毎回スキャンだった。
- **正規表現ヒントは英語表記の書類を前提にしている。** 一部書類は中国語表記
  であることをファイル名から確認しており、英語キーワード前提のヒントでは
  拾えない可能性が高い（v0では未対応）。
- **複数行にまたがる値は非対応。** SELLER/BUYER等の住所欄が複数行にまたがる
  場合、v0は1行分しか拾わない。
- **xlsx抽出は行単位のセル連結テキストへの正規表現一致のみ。** 「ラベル列」
  「値列」に分かれた典型的な表形式は苦手（連結テキストがラベルと値を
  タブで単純につなげただけになる）。
- **評価管理表のヘッダー行検出もヒューリスティック。** 先頭N行のうち
  「ラベルらしいセルが最多の行」を機械的に選んでいるだけで、結合セルは
  openpyxl標準動作のまま（左上セル以外は空扱い）。
- **もっとも重要な既知の限界:** 今回のv0実行では、fields.yamlの27フィールド中
  26フィールドが、10案件すべてで評価管理表のどの列にも対応付けられなかった
  （残り1フィールド「保険」は全案件で対応付いたが、AI側がそもそも値を
  抽出できておらず比較不能だった）。つまり**この答え合わせの組み合わせでは
  実質的な一致率が測れなかった**。原因は次の2つのどちらか、もしくは両方:
  1. フィールドラベルの表記ゆれ吸収（同義語・英語エイリアス）が未整備
  2. 評価管理表（工場評価・格付け用の帳票）自体が、通関申告ヘッダー系の
     このフィールドスキーマの答え合わせ対象として想定と大きく違う可能性
     （評価管理表は多シート・多行の格付け表で、通関ヘッダー項目とは
     そもそも性質が違う書類に見える）

## 客先確認リスト

- **FMの狙い先** … どのFileMakerテーブル/レイアウトに書き込む想定か（未確定）
- **確認UI一本化** … 抽出候補を人が確認・修正する画面をどこに一本化するか
  （FM内蔵の画面か、別ツールか）
- **無人書込み可否** … 人の確認なしにFMへ自動書込みしてよい条件があるか、
  それとも常に人手確認必須か
- **FM受け口とバージョン** … 受け側FileMakerのバージョン・連携方式
  （ODBC / スクリプト / CSV取込 等）
- **機密情報取り扱いの書面承諾** … 本件書類を対話型セッションで扱ってよいか
  （`engines/claude_interactive.py` のNFR-1-EX条件にも関わる。現状は書面承諾の
  有無を確認できておらず、対話型エンジンは未実装のスタブのまま）
- **評価管理表の位置づけ** … 今回の答え合わせに使った評価管理表が、この
  フィールドスキーマの正しい比較対象なのかどうか（上記「既知の限界」参照）
- **OCR導入方針** … 要OCR書類（全体の約46%）にどこまで投資するか
  （ローカルOCR導入 / クラウドOCR / 人手継続のいずれか）
